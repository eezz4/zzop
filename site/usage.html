Using zzop

zzop ships two Node-free native binaries over one shared library: no Node.js, no npm, nothing to compile. They are driven completely differently, so pick one before you install — the two cards below are the whole decision. For the input/output JSON contract both surfaces share (AnalyzeRequest in, AnalyzeOutputView out), see the Reference.

Pick one

Which binary do you want?

zzop-mcp — for your AI agent

An MCP server over stdio, for Claude Code, Claude Desktop or any MCP client. Install the plugin or the .mcpb bundle and the agent calls the tools to answer questions about your repos — you run no commands. See the MCP surface.

zzop — for a terminal or CI

A plain CLI, for running analyses yourself in a terminal, a CI job or a script. zzop analyze ., zzop cross ./web ./api, … JSON to stdout, ESLint-style. See every subcommand.

Both dispatch to the same shared handlers over the same engine, so a tool call and a CLI run against the same path analyze identically and reach the same verdict. The findings-list filters reach both: analyze_repo/cross_repo/analyze_envelope accept severity (minimum severity), rule (an exact rule id) and limit (list cap, default 50, max 1000), and their CLI twins analyze/cross/analyze-envelope take the same three as --severity/--rule/--limit, parsed into the same shared filter — so neither surface can filter differently. Counts by severity and rule cover everything on both surfaces either way; the cap truncates only the listed findings, and truncation is always disclosed. What still differs: some lanes are CLI-only, with no MCP tool twin at all: manifest, diff, facts, coverage, graph, explain and init. Neither binary makes a network request of any kind.

Install

Install & first run

Four ways to get it — no source checkout or toolchain required for any of them. The first two are the agent lane (they install zzop-mcp for you); the last two are the CLI lane, and the release-asset lane serves either binary:

  • Claude Code — /plugin marketplace add eezz4/zzop, then /plugin install zzop@zzop. The plugin's plugin.json declares the MCP server and runs zzop-mcp mcp for you. On the first session it fetches its own binary during startup, after the tool list is settled, so restart Claude Code once before the zzop tools show up.
  • Claude Desktop — the one-click .mcpb bundle (drag-and-drop install); it carries the platform binary. See packages/mcpb/README.md.
  • CLI / CI — download the zzop-cli-<platform>[.exe] binary from GitHub Releases (5 platforms) and put it on PATH as zzop. Want the MCP server instead? Download zzop-mcp-<platform>[.exe] the same way and put it on PATH as zzop-mcp.
  • npm — npm i -g @zzop/cli (or npx @zzop/cli): a zero-logic shim that spawns this exact native binary, fetched per-platform as an npm dependency, no separate Node SDK involved. See packages/cli/README.md.
First run, either lane
# CLI lane — you type this:
zzop init                  # write the starter config — REQUIRED once per tree
zzop analyze .             # analyze this tree, print JSON findings
zzop cross ../api ../web   # cross-layer join across 2+ trees (each needs its own config)

# MCP lane — a client runs this for you; you never type it:
zzop-mcp mcp               # serve MCP over stdio for Claude Code/Desktop

See packages/README.md for the full reference on both.

Agent lane

The zzop-mcp surface

zzop-mcp has no analysis subcommands: a bare zzop-mcp and the explicit zzop-mcp mcp both serve MCP over stdio (newline-delimited JSON-RPC 2.0), and version/--version (plus version --verbose, which adds every parser's fingerprint) and help/--help/-h are the only other forms. Every analysis reaches it as a tools/call. It announces its own version on stderr at startup, which an MCP client shows in its server log.

Tool · CLI twinWhat it answers
analyze_repozzop analyzeAnalyze one repository/tree path.
cross_repozzop crossAnalyze 2+ trees and join them across the layer boundary.¶
check_filezzop fileWhat does zzop know about THIS FILE? Uncapped, sealed verdict.¶
check_endpointzzop endpointIs one io key provided, consumed or joined? One sealed verdict.¶
analyze_envelopezzop analyze-envelopeMode A: a full Normalized-AST envelope replaces native parsing for this run.
validate_envelopezzop validate-envelopeValidate a Normalized-AST envelope against its contract, offline.
validate_rule_packzzop validate-rule-packValidate a DSL rule pack's structure before loading it, offline.

Four of the seven answer in one line and have no more to say. The other three carry the contract a caller has to know before trusting the reply:

cross_repo

The join itself: frontend calls matched against backend routes, shared DB tables, route drift. It runs the same engine path as its CLI twin, so the zzop cross detail describes both source modes.

check_file

Definitive "what does zzop know about THIS FILE?" — tree, symbols, io facts, dependency edges both ways and every finding anchored there, uncapped. Its sealed verdict says whether the file was analyzed, not whether it is healthy. The full verdict vocabulary and the multi-tree tie-break are in the zzop file detail.

check_endpoint

Definitive "is io key X provided/consumed/joined?" — one sealed verdict rather than bucket counts to eyeball. The pattern is matched as a case-insensitive substring against any cross-layer io key (http routes, env keys, DB tables, topics). The eight-token verdict vocabulary is in the zzop endpoint detail.

Alongside the tools, a resources/* surface serves the embedded authoring-contract documents at zzop://contract/<name> — the envelope schema and guide, the adapter guide, a byte-pinned key-normalization fixture, a minimal worked envelope, the DSL reference and authoring guide, the rule-pack schema, the config surface, an annotated starter config and the full rule catalog — so a custom parser adapter, a rule pack or a zzop.config.jsonc can be written with nothing but this binary and no source checkout. The same documents print to a terminal via zzop contract [<name>]. Relative path/configPath arguments resolve against the server process's working directory, so pass absolute paths. Exact argument shapes and the output-truncation contract: docs/modules/mcp.md.

CLI lane

The zzop CLI and zzop.config.jsonc

zzop.config.jsonc is JSON with comments and trailing commas allowed. zzop analyze <path> auto-discovers one at the tree root; every subcommand that takes a tree also takes --config <path> to load one from anywhere else (the USAGE line is the canonical list). zzop init [<dir>] writes a starter file into <dir> (default: the current directory) — every optional key annotated with what it means, each set to zzop's own value, so it documents the defaults instead of changing them; it refuses to overwrite an existing config without --force. Running it is required once per tree — every analysis lane refuses a tree that has no config, because the vocabulary block holds the names zzop would otherwise guess about your project and an undeclared key is a judgment zzop does not make. The same document prints without writing anything as zzop contract config-template. Hand-writing one from the reference below is equally fine, and zzop contract config-surface prints the machine-checked vocabulary of every known key.

zzop.config.jsonc
{
  // What to analyze: one or more directory roots. Multiple roots run a
  // cross-layer (multi-tree) analysis.
  "roots": ["."],

  // Or name each tree explicitly (takes precedence over "roots"):
  // "trees": [
  //   { "root": "./api", "sourceId": "api" },
  //   { "root": "./web", "sourceId": "web" }
  // ],

  "packs": {
    // Extra directories of custom DSL rule packs. These MERGE with the
    // bundled packs; a custom pack whose id matches a bundled one wins.
    // Omit this key entirely and "zzop/rules" is discovered by default when
    // it exists. Declaring it replaces that default outright (never merges
    // with it); declaring it as [] is the explicit "no pack directories".
    "extraDirs": ["./zzop/rules"],
    // Whole packs to disable, by pack id. Which ones? Read "packsLoaded" in
    // the output: a pack with "filesInScope": 0 matched no file path in this
    // tree, so it can only ever report zero here -- and the run says so in
    // "warnings", naming every such pack. Disabling one stops its rules from
    // being evaluated at all. It is a path fact, not a stack fact: add a file
    // that matches and the pack applies again, so keep the ones you may grow
    // into. Nothing is disabled for you.
    "disabled": ["browser"],
    // The same gate read the other way: an ALLOWLIST. Name the packs you want
    // and every other bundled pack stays off, so a repo that cares about one
    // subject writes one line instead of eleven. Absent or [] means no
    // allowlist at all (every pack runs) -- never "allow nothing". The two
    // compose: "only" selects, "disabled" still subtracts. Both are about
    // PACKS -- native analyses (dead-candidates, the score channels) are not
    // packs and keep running; switch those off by id under "rules".
    "only": ["security", "sql"]
  },

  "rules": {
    // "off"                        -> disable the rule
    "sql/count-in-loop": "off",
    // "info" | "warn" | "critical" -> override severity
    "sql/nplus1": "warn",
    // object form -> override severity AND drop findings by file path. Each
    // "exclude" entry is a plain substring, or a glob if it has * ? or {}.
    "sql/race-condition-toctou": { "severity": "warn", "exclude": ["legacy/", "**/*.gen.ts"] }
  },

  // Enables git-history-derived signals. Omit to use engine defaults.
  "git": { "recentDays": 30 },

  // Analysis cache directory, resolved against THIS FILE's directory. Omitting
  // the key does not turn caching off: a config-file run defaults
  // to ".zzop/cache" and creates it on the first run, inside the tree you
  // analyze. Add an anchored "**/.zzop/" to .gitignore (never a "zzop*" glob --
  // that would also swallow an authored "zzop/" rule-pack directory). Set the
  // key to null to turn caching off and write nothing.
  "cacheDir": ".zzop/cache",

  // The names YOUR project picks, which zzop would otherwise have to guess:
  // what you call your auth guards, which URL segments mark your API, where
  // your sources live, which directories are build output. Every value in the
  // starter file is zzop's own suggestion for that key, written out so you can
  // judge it -- NOT a default applied behind the config: an undeclared key
  // makes no judgment at all, so writing this block turns those questions on
  // and deleting a key turns one off. Editing a key replaces that whole list
  // or pattern, and the keys you leave alone keep theirs. Run "zzop init" to
  // get the block filled in.
  "vocabulary": {
    "authGuardPattern": "(?i)(auth|guard|verify|session|token|permission|acl|owner|admin|role|(?:has|can|check|require)access)",
    "apiSegmentPattern": "(?i)/(api|graphql|rpc|v[0-9]+)(/|$)",
    "skipDirs": ["node_modules", "dist", "build", ".next", ".git", "target", ".yarn", ".zzop", "zzop-reports", ".zzop-cache"]
    // ...and authGuardQualifierTokens, authAcquisitionStandalonePattern,
    // authAcquisitionConditionalPattern, authFamilyPathPattern,
    // javaSourceRoot, pythonPackageRoots, workspaceSkipDirs
  },

  // Files larger than this many bytes skip structural parsing.
  "sizeCap": 1500000
}

Two directories, one letter apart. .zzop/ is zzop's — derived, disposable, ignored (today just .zzop/cache/). zzop/ is yours — hand-authored and committed: custom rule packs in zzop/rules/, adapter overlays in zzop/adapters/. Ignore the first with an anchored **/.zzop/ and never a zzop* glob: a glob matches both and would quietly take your rule packs out of version control, with no error from git and nothing wrong-looking in the diff.

Config severities normalize to the engine's three levels — off/none/disabled disable a rule; info/note/low → info; warn/warning/medium → warning; error/critical/high → critical.

Design notes — keys this front end no longer recognizes

failOn, format and report.* were config keys left over from a CLI removed in 2026-07. They were accepted and then ignored — no warning, no error, no behavior. As of 2026-07-26 they are no longer recognized, so writing one produces a configWarnings entry naming it as removed and pointing at the remedy. Deleting such a key changes nothing about a run. The repo-side record of the same removal is docs/getting-started.md.

Details — analyze

zzop analyze <path> / analyze --config <zzop.config.jsonc>

Analyze one repo/tree, print a JSON findings summary. The path form auto-discovers <path>/zzop.config.jsonc; the --config form names a config at any location (for one that does not sit at the tree root), and the reply echoes the tree root it actually analyzed rather than the config file. Exactly one of the two, and a config declaring 2+ trees is a guided error pointing at the cross-layer join instead.

zzop cross <path>... / cross --config <zzop.config.jsonc>

Analyze 2+ trees and print the cross-layer join — zzop's headline. Paths mode needs 2+ roots and loads each root's own zzop.config.jsonc (a root that has none is refused, exactly as a single-tree run of it would be); config mode's trees array defines the join.

zzop analyze-envelope <envelope.json>

Mode A: the envelope file replaces native parsing entirely for this run; prints the same JSON findings summary shape as analyze.

Details — query

zzop file <path> <tree>... / file <path> --config <path>

Definitive "what does zzop know about THIS FILE?" query — the targeting twin of endpoint with a file path as the target: the tree it belongs to, its symbols, io facts, dependency edges in both directions, and every finding anchored in it. Uncapped, unlike every summary lane: a single file is bounded, so nothing is dropped and there is nothing to disclose.

The sealed verdict (analyzed / lexical-only / degraded / not-found) answers whether the file was analyzed, not whether it is healthy — an empty findings list means "clean" for the first and "nothing structural ever ran" for the next two. As with endpoint, the reply carries verdictMeaning — the returned token's own definition, shipped with the answer so the vocabulary has exactly one owner. A path found in more than one tree names the tree it answered from and lists the rest rather than picking silently; a not-found reply lists the nearest walked paths.

zzop endpoint <pattern> <path>... / endpoint <pattern> --config <path>

Definitive "is io key X provided/consumed/joined?" query: pattern is substring-matched against every cross-layer io key, answered with a sealed verdict (linked / provided-only / consumed-unprovided / external / unresolved-only / ambiguous / mixed / not-found). The reply also carries verdictMeaning — the returned token's own one-sentence definition, shipped with the answer so the vocabulary has exactly one owner and every surface reads it from there.

zzop facts <path>... / facts --config <zzop.config.jsonc>

Print the run's post-assembly facts — the same source modes and engine path as cross, projected as facts instead of a verdict: per tree its sourceId, coverage, warnings and the whole commonIr (dep graph, symbols, loc, io — file and line intact, which is exactly what manifest strips), plus every crossLayer bucket, the run-level warnings, the disclosure registry and a tool fingerprint. Deliberately uncapped, for the same reason manifest is: a rule computed over a truncated world is silently wrong.

This is the consumer half of the custom-rule extension point — the workflow is zzop facts ./api ./web > facts.json && ./my-rule facts.json, so zzop emits what it knows and your program decides what is a problem. It neither spawns your program nor ingests its findings back, both deliberately. Every key is always present (an empty bucket is [], never absent), so you never have to read a missing key as either "zero" or "did not run". Full field table: docs/modules/facade.md.

zzop coverage <path>... / coverage --config <zzop.config.jsonc>

The aggregate-visibility view — "how much of this tree does zzop actually see?" Per tree it prints an extension-by-dispatch table (how many files got a structural projection, how many were walked lexical-only, how many degraded), the tree's own engine warnings forwarded verbatim (the framework-silence self-reports ride there), the per-tree coverage census verbatim, and joinVisibility as counts (provides, consumesKeyed, consumesUnresolved) plus a meaning, rather than a bare boolean or a lone sentence — the sentence alone read identically at one keyed consume and at four hundred.

Design notes — what each cell means, and why there is no single score

Each dispatch class ships its meaning in the reply as dispatchMeaning, so 0 findings on a lexical-only extension can never read as "clean" — plus inDepGraph per row: how many of that extension's files contribute at least one resolved import edge, so 91 parsed files with 2 resolving is visible as import-resolution blindness instead of a bare tree-wide edge count. A walkNote appears when files under .git/ were walked (a config that declares no vocabulary.skipDirs skips nothing — the note names the count and the fix).

blindSpots is the capability axis: per-rule evidence blind spots derived from the sightline declarations compiled into this build, crossed with the tree's structural extensions, with blindSpotBasis stating what was crossed so an empty list is never ambiguous.

Deliberately no single score. Every cell is one of three kinds — measured this run, a capability of this build, or never measured — and the never-measured axes (recall: how many of the findings that exist zzop reports, which has been measured on zzop's own labeled corpus but never on yours) ride in an unmeasured array that is a schema field, not a caveat sentence, precisely so it cannot be dropped when the numbers are quoted. Folding the measured axes into one number would present it as an answer to the question that axis leaves open.

zzop graph <path>... / graph --config <zzop.config.jsonc>

Print one picture of the run as text for an external renderer — zzop draws nothing; it serializes one standard format and every viz stack stays outside. --domain picks which picture, and each draws different nodes:

--domain joinThe cross-layer join over io keys. The default.
--domain depThe file import graph, with cycles marked — the only NDJSON domain.
--domain riskThe blast-radius hubs and extraction seams.
--domain postureThe mutating routes and their guard status.
--domain cochangeFile pairs that keep being committed together — from git history.
--formatThe serialization: mermaid (default, every domain) · cosmograph-nodes / cosmograph-links (dep only).
--fold <n>Draw each path's first n segments as one box — dep and cochange only.
--scope <prefix> · --top <n>Keep rows whose source id or site path starts with the prefix · cap what is drawn.

cochange is the only domain drawn from git history rather than imports, which is the point of having it: on this repository its densest constellation is the eight shipped THIRD-PARTY-NOTICES.md copies, which have zero import edges between them and still must never diverge. --fold answers the other question — what a node is: --domain dep --fold 2 turns a thousand-file import graph into the module map it was always a picture of, and --fold 1 into the top-level one. The mermaid form is a flowchart that renders inline anywhere, with no toolchain; the two NDJSON tables are for an interactive viewer and load into Cosmograph, Gephi or any force-graph library with no conversion — this repository's own graph is that output, drawn by a viewer.

Design notes — what a fold costs, which columns exist, and how every cap is disclosed

cochange is a sample, never a repository total. The underlying map keeps only commits touching 2..=25 files (a sweeping refactor says nothing about which two files belong together) and only each file's top 10 partners, and both filters are stated inside the document.

A fold is the same graph with coarser endpoints, not a second measurement. It applies to dep and cochange — the domains whose nodes are paths — and is refused elsewhere rather than ignored, because risk/posture nodes are engine verdicts and join nodes are io keys, and neither has a path granularity to coarsen. Three things a fold costs, each disclosed in the document rather than avoided: a folded edge is labelled with the number of file-level edges it collapsed and nothing else (summing a co-change edge's commit counts across pairs would produce a number larger than the repository has commits); the depth is a convention, not a fact about your tree, so the census prints both node counts and a tree that keeps everything under one directory is visible as a one-box picture rather than felt as a boring one; and a path with fewer segments than the depth stands for itself, counted separately so a lone file never reads as a module. --scope is applied before the fold and --top after, so each keeps its own meaning and the fold's loss is reported against its own denominator.

The NDJSON tables are emitted uncapped. An import graph outgrows a drawn picture long before it outgrows a viewer with zoom, so --top is refused there rather than quietly ignored, and the census goes to stderr so stdout stays a parseable table. The columns are the ordinary ones (source/target/endpointsInCycle for links; id/source/path/label/folder/fanIn/fanOut/degree/inCycle for nodes). Those nine are structural — read off the graph itself, so every node has them.

Nodes also carry the axes the run measured, which is what makes a thousand-node picture readable rather than a thousand identical dots: loc for size, and — when git collection ran — authorCount/changeCount/churn/lastModified for colour. No flag adds or removes a column; every axis is always offered and the viewer picks. What varies is whether a given row has the key: an axis this run did not measure is omitted, never written as 0, because churn: 0 would say "this file never changed" in the same bytes as "nobody looked" and a viewer colouring by it would draw the second as the first. Omitting a column is honest but silent, so the stderr census also reports the coverage — loc on N of M row(s), git history on N of M — which is where you look when your viewer offers no colour-by-churn.

Scoped by design. --top caps what is drawn — per bucket on join, where the many call sites of one key/source collapse into one node first so the cap is never spent on duplicates — and its default is per domain, because their densities differ (join 25, dep 40, risk 12, posture 20, cochange 30): a join has tens of relations where an import graph has thousands. Every cap and filter is disclosed inside the document — a %% census line per bucket (drawn/inScope/total from N site(s)) plus a visible note node, because comments do not survive rendering.

What it deliberately does not render: per-site file and line (nodes aggregate call sites — use facts for those), and the drift/near-miss verdicts in crossLayerFindings, which are findings about the join with no node identity of their own — drawing them would mean inventing facts the IR does not have. Items carrying neither a key nor a raw string are counted as an unlabelable remainder, never guessed.

Details — contract

zzop manifest <path>... / manifest --config <zzop.config.jsonc>

Print the run's structural contract manifest — the same two source modes and the same engine path as cross, projected to IDENTITY only: provides ({kind, key, source}), edges ({kind, key, from, to}), buckets ({bucket, kind, key, source}), per-source {sourceId, joinContributionZero, degraded}, and a tool fingerprint — this build's release version plus every parser's own fingerprint, which is what makes the honesty gate on diff possible (note this is NOT what zzop version prints: that is the bare release number).

No file, no line, no root path, no findings — a pure refactor that moves files produces an EMPTY diff — and deliberately no caps, which is the whole point: above the reply's edges cap, two runs agree on the bucket COUNTS while neither can say which route left the join. The workflow is file-shaped: commit a manifest next to the code the way a lint baseline file is committed, and compare a later run against it with diff. zzop never stores, names, or cleans up a snapshot — that is yours.

zzop diff <a.json> <b.json> [--allow-tool-drift]

The delta between two manifests — pure, no analysis and no filesystem beyond the two files. Read transitions first: a + is common and usually harmless, but a key whose bucket placement CHANGED — edges → unprovidedConsumes — means the caller still calls a route that is gone, i.e. a broken contract. The per-relation added/removed lists are that reading's raw evidence, not extra facts.

Two honesty gates. Manifests from different zzop builds are refused by default (our own parser improvement would otherwise read as the other team breaking a contract) — --allow-tool-drift compares anyway and stamps a toolDrift block naming both builds. And every removal attributable to a source that got LESS visible is tagged blindnessSuspect, with sources.coverageDropped naming the drop, so "the route vanished" is never reported when "we stopped being able to see it" is the honest reading.

zzop contract [<name>]

No name lists the embedded authoring-contract resources (schemas, guides, the rule catalog, config-surface); a name prints that document's exact bytes to stdout. They are the same bytes the MCP resources/* surface serves, so a terminal and an agent read one document.

zzop explain <rule-id> [--config <path>]

Print one DSL rule's data (id, pack, severity, message, derived suppress marker with the comment leaders that matcher kind honors, matcher kind, and every exclusion field that kind actually carries — exclude_pattern/file_exclude_pattern for line-scan, absent/file_exclude_pattern for method-scan, file_exclude_pattern/anchor_exclude_pattern for io-scan, none for symbol-scan — with its real value) straight from the rule data itself, never docs/rules/catalog.md prose. Accepts the full <pack>/<rule> id or a bare <rule> id when unambiguous.

Which packs are searched is the one thing you choose: without --config it reads the packs compiled into this binary; with it, the packs that config's trees load — the compiled-in ones plus every zzop/rules/ and packs.extraDirs directory those trees name. Use the second form for a rule you recovered from an exported pack: such a rule runs and reports findings under its id, so a lookup that only reads compiled-in packs would call that same id unknown. It says so — the bare form's unknown-id message names --config.

Design notes — two answers worth knowing before you need them

An io-scan rule's marker is printed with its run-mode condition attached — native-parse runs only: an envelope carries no source text for the finding's anchor line, so in analyze-envelope mode no marker there suppresses anything and you disable the id or exclude the path instead. (A symbol-scan rule answers none for the same class of reason: its findings have no line to anchor a comment against.)

A bare namespaced native id — the tail alone (god-model, route-near-miss) of a schema/ or cross-layer/ id — is not a rule id this lookup can render, so it comes back as a guided failure (stderr, exit 1) that names the full id, because disabledRules and severityOverrides match ids exactly and the bare form would configure nothing.

Details — validate & misc

zzop validate-envelope <envelope.json>

Offline "is this envelope well-formed?" check. Prints {"valid":…,"issues":[…],"hints":[…]}; exits 0 valid / 1 invalid. The two lists are different axes: issues reject the envelope and alone decide valid — and therefore the exit code, which hints never changes — while hints are shapes zzop accepts that are almost certainly not what you meant.

What a hint costs you depends on the shape — some make the cross-layer join find nothing at all, others still join and instead change what the run produces — so each hint states its own consequence and its fix rather than leaving you to a blanket claim; the checks themselves are the list (see validate_envelope in docs/modules/mcp.md). So a valid envelope with a non-empty hints exits 0 and is usually the more urgent read. hints is always present, empty array included, so "we looked and found nothing" is never confused with a build that has no hint pass.

zzop validate-rule-pack <pack.json>

Offline "does this DSL pack load, and can every rule in it actually fire?" check — bad shape, uncompilable matcher regex, and the structural dead-rule shapes (nothing to match, trigger naming an undeclared label). Same {valid,issues}/exit-code contract as validate-envelope, minus the hints list — deliberately: rule packs have no hint pass, and shipping an always-empty array would claim a search that never ran.

zzop init [<dir>] [--force]

Write the embedded starter zzop.config.jsonc — the config-template document above — into <dir> (default: the current directory; the directory must already exist — init writes a config into a tree, it never creates one). It generates nothing: the bytes are the same ones zzop contract config-template prints and MCP resources/read serves, so the three surfaces cannot disagree. Every key in it is annotated with what it means and set to zzop's own value, which makes writing it a starting point you can then edit.

Every analysis lane requires it; the lanes that produce or describe it (init, contract, explain, version, help, validate-envelope, validate-rule-pack) and analyze-envelope (no tree, so nothing to configure) do not. An existing config file is never overwritten without --force (the refusal exits 1).

zzop version · zzop help · zzop <subcommand> --help

version / --version prints the binary's version (the same value MCP's initialize reports as serverInfo.version). The bare form stays one token so a script can parse it; version --verbose adds every parser's fingerprint — which parser FRONTEND read the files, an ID rather than a per-build hash — and prints the identical string zzop-mcp version --verbose does.

help / --help / -h prints the usage line plus one elaboration per subcommand, exit 0 (the zzop-mcp server binary has its own help). zzop <subcommand> --help prints just that subcommand's own line, to stdout, exit 0: a help request is answered rather than rejected — it used to fall into the dash-shaped-argument guard and leave with exit 2 on stderr.

Exit codes

Exit codes are uniform across every subcommand: 0 = ran successfully; 1 = a runtime failure (unreadable path, invalid envelope/config) — for validate-envelope/validate-rule-pack specifically, 1 instead means "ran fine, found the input invalid"; 2 = an argument-shape mistake (missing/extra/flag-shaped argument). There is no severity-gated CI exit code, and no config key that claims to add one; gate a build by parsing the JSON output's findings/crossLayerFindings severities yourself.

Adapt to your stack

Making zzop fit your environment

No two repositories are the same shape, and zzop is meant to be tuned to yours rather than run one-size-fits-all. Every way in is data, not an engine fork:

  • Custom rule packs. Rules are JSON. Put a pack of your own conventions in zzop/rules/ and it is discovered without your naming it (or point packs.extraDirs somewhere else) — a custom pack whose id matches a bundled one wins. The rule catalog shows the shape; zzop validate-rule-pack <pack.json> checks one before you ship it. Full DSL reference: docs/rules/authoring-guide.md.
  • Parser injection for what the engine can't read natively. A language or framework zzop doesn't parse — or a hand-rolled HTTP client it can't see — need not be a blind spot. An external adapter (any language) emits a Normalized-AST envelope, in one of two shapes named after the engine entry point that consumes it: analyzeEnvelope (Mode A — a full envelope that replaces native parsing for a run, via zzop analyze-envelope) or adapterOverlays (Mode B — just the IO/fragment facts for a few files, merged on top of native analysis). Worked adapters ship in the repo (OpenAPI-SDK, Svelte, wrapper, react-query). See NORMALIZED_AST.md and the adapterOverlays field.
  • Topology facts only you know. A gateway mount prefix, which hosts a tree owns, a route zzop couldn't resolve from source — declare them in config (mounts / mountedAt / hosts / routes) so the cross-layer join sees your real deployment shape, not just what's literal in the source.

This is where zzop pairs naturally with an AI agent over MCP: the agent runs an analysis, reads the coverage census and warnings to see exactly what came back dark (a channel with zero extraction, a language with no native parser), and you tune the config or add an adapter together until the map is complete. The tool tells you what it cannot see instead of guessing — so the loop converges on your environment.

Findings

Suppressing & disabling findings

DSL pack rules (the security/hardcoded-secret, sql/nplus1-style ids) each carry an inline suppress marker — a short comment placed in the flagged code, e.g. // zzop-hardcoded-secret-ok — that silences just that occurrence. The marker is derived from the rule id, so you never look it up: strip the pack prefix from the finding's id, then wrap it as zzop-<rule id>-ok (sql/nplus1 → // zzop-nplus1-ok). Because it is derived and not stored, renaming a rule renames its marker with it. Native analyses are disable-only via config, with two comment-driven exceptions: non-idempotent-write/unsafe-read-endpoint honor a hand-written // idempotent-ok: <reason> on the handler's body-start line or up to 3 lines above it (trailing colon required), and dead-candidates/unimported-export skip files carrying a generated-file banner (@generated and friends) in their first 8 lines.

Disable a native analysis
{
  "rules": {
    "dead-candidates": "off",
    "cross-layer/unconsumed-endpoint": "off"
  }
}

Embedders pass the same ids through disabledRules instead of the rules: { "<id>": "off" } config shape.
