Using zzop

zzop ships two Node-free native binaries over one shared library: no Node.js, no npm, nothing to compile. zzop is the CLI, run over subcommands (zzop analyze . — no code, ESLint-style); zzop-mcp is the MCP stdio server for MCP clients (zzop-mcp mcp). This page covers the zzop CLI. For the input/output JSON contract every surface shares (AnalyzeRequest in, AnalyzeOutputView out), see the Reference.

Command line

Install & run the binary

Four ways to get it — no source checkout or toolchain required for any of them:

  • Claude Code — /plugin marketplace add eezz4/zzop, then /plugin install zzop@zzop. The plugin's plugin.json declares the MCP server and runs zzop-mcp mcp for you. On the first session it fetches its own binary during startup, after the tool list is settled, so restart Claude Code once before the zzop tools show up.
  • Claude Desktop — the one-click .mcpb bundle (drag-and-drop install); it carries the platform binary. See packages/mcpb/README.md.
  • CLI / CI — download the zzop-cli-<platform>[.exe] binary from GitHub Releases (5 platforms) and put it on PATH as zzop. Want the MCP server instead? Download zzop-mcp-<platform>[.exe] the same way and put it on PATH as zzop-mcp.
  • npm — npm i -g @zzop/cli (or npx @zzop/cli): a zero-logic shim that spawns this exact native binary, fetched per-platform as an npm dependency, no separate Node SDK involved. See packages/cli/README.md.
Analyze a tree
zzop analyze .        # analyze this tree, print JSON findings
zzop cross ../api ../web   # cross-layer join across 2+ trees
zzop-mcp mcp               # serve MCP over stdio for Claude Code/Desktop

See crates/host/README.md for the full CLI reference.

CLI config

zzop.config.jsonc

zzop.config.jsonc is JSON with comments and trailing commas allowed. zzop analyze <path> auto-discovers one at the tree root; cross/endpoint load one explicitly via --config <path>. There is no scaffolding command to generate a starter file (the JS CLI's zzop init was dropped, not ported) — hand-write it from the reference below, or run zzop contract config-surface to print the machine-checked vocabulary of every known key.

zzop.config.jsonc
{
  // What to analyze: one or more directory roots. Multiple roots run a
  // cross-layer (multi-tree) analysis.
  "roots": ["."],

  // Or name each tree explicitly (takes precedence over "roots"):
  // "trees": [
  //   { "root": "./api", "sourceId": "api" },
  //   { "root": "./web", "sourceId": "web" }
  // ],

  "packs": {
    // Extra directories of custom DSL rule packs. These MERGE with the
    // bundled packs; a custom pack whose id matches a bundled one wins.
    "extraDirs": ["./zzop/rules"],
    // Whole packs to disable, by pack id.
    "disabled": ["browser"]
  },

  "rules": {
    // "off"                        -> disable the rule
    "typescript/no-explicit-any": "off",
    // "info" | "warn" | "critical" -> override severity
    "sql/nplus1": "warn",
    // object form -> override severity AND drop findings by file path. Each
    // "exclude" entry is a plain substring, or a glob if it has * ? or {}.
    "sql/race-condition-toctou": { "severity": "warn", "exclude": ["legacy/", "**/*.gen.ts"] }
  },

  // Enables git-history-derived signals. Omit to use engine defaults.
  "git": { "recentDays": 30 },

  // Analysis cache directory, resolved against THIS FILE's directory. Omitting
  // the key does not turn caching off: a config-file / zero-config run defaults
  // to ".zzop/cache" and creates it on the first run, inside the tree you
  // analyze. Add an anchored "/.zzop/" to .gitignore (never a "zzop*" glob --
  // that would also swallow an authored "zzop/" rule-pack directory). Set the
  // key to null to turn caching off and write nothing.
  "cacheDir": ".zzop/cache",

  // Files larger than this many bytes skip structural parsing.
  "sizeCap": 500000,

  // "format" / "report.*" / "failOn" are recognized (no unknown-key warning)
  // for forward-compat with the removed JS CLI's config files, but zzop-mcp
  // does not act on them today: output is always the JSON summary on stdout,
  // and the exit code reflects only whether the run itself succeeded (see
  // "Exit codes" below) — gate on a specific severity by parsing the JSON.
  "format": "pretty",
  "failOn": "warn"
}

Config severities normalize to the engine's three levels — off/none/disabled disable a rule; info/note/low → info; warn/warning/medium → warning; error/critical/high → critical.

CommandDescription
zzop analyze <path>Analyze one repo/tree, print a JSON findings summary. Auto-discovers <path>/zzop.config.jsonc; a config declaring 2+ trees is a guided error pointing at cross instead.
zzop cross <path>... / cross --config <zzop.config.jsonc>Analyze 2+ trees and print the cross-layer join — zzop's headline. Paths mode needs 2+ roots and ignores any per-tree config; config mode's trees array defines the join.
zzop endpoint <pattern> <path>... / endpoint <pattern> --config <path>Definitive "is io key X provided/consumed/joined?" query: pattern is substring-matched against every cross-layer io key, answered with a sealed verdict (linked / provided-only / consumed-unprovided / external / unresolved-only / ambiguous / mixed / not-found).
zzop manifest <path>... / manifest --config <zzop.config.jsonc>Print the run's structural contract manifest — the same two source modes and the same engine path as cross, projected to IDENTITY only: provides ({kind, key, source}), edges ({kind, key, from, to}), buckets ({bucket, kind, key, source}), per-source {sourceId, joinContributionZero, degraded}, and a tool fingerprint — this build's release version plus every parser's own fingerprint, which is what makes the honesty gate on diff possible (note this is NOT what zzop version prints: that is the bare release number). No file, no line, no root path, no findings — a pure refactor that moves files produces an EMPTY diff — and deliberately no caps, which is the whole point: above the reply's edges/bucketKeys caps, two runs agree on the bucket COUNTS while neither can say which route left the join. The workflow is file-shaped: commit a manifest next to the code the way a lint baseline file is committed, and compare a later run against it with diff. zzop never stores, names, or cleans up a snapshot — that is yours.
zzop diff <a.json> <b.json> [--allow-tool-drift]The delta between two manifests — pure, no analysis and no filesystem beyond the two files. Read transitions first: a + is common and usually harmless, but a key whose bucket placement CHANGED — edges → unprovidedConsumes — means the caller still calls a route that is gone, i.e. a broken contract. The per-relation added/removed lists are that reading's raw evidence, not extra facts. Two honesty gates: manifests from different zzop builds are refused by default (our own parser improvement would otherwise read as the other team breaking a contract) — --allow-tool-drift compares anyway and stamps a toolDrift block naming both builds; and every removal attributable to a source that got LESS visible is tagged blindnessSuspect, with sources.coverageDropped naming the drop, so "the route vanished" is never reported when "we stopped being able to see it" is the honest reading.
zzop analyze-envelope <envelope.json>Mode A: the envelope file replaces native parsing entirely for this run; prints the same JSON findings summary shape as analyze.
zzop validate-envelope <envelope.json>Offline "is this envelope well-formed?" check. Prints {"valid":…,"issues":[…]}; exits 0 valid / 1 invalid.
zzop validate-rule-pack <pack.json>Offline "does this DSL pack load, and can every rule in it actually fire?" check — bad shape, uncompilable matcher regex, and the structural dead-rule shapes (nothing to match, trigger naming an undeclared label). Same {valid,issues}/exit-code contract as validate-envelope.
zzop contract [<name>]No name lists the embedded authoring-contract resources (schemas, guides, the rule catalog, config-surface); a name prints that document's exact bytes to stdout.
zzop explain <rule-id>Print one bundled DSL rule's compiled-in data (id, pack, severity, message, derived suppress marker with the comment leaders that matcher kind honors, matcher kind, and every exclusion field that kind actually carries — exclude_pattern/file_exclude_pattern for line-scan, absent/file_exclude_pattern for method-scan, file_exclude_pattern/anchor_exclude_pattern for io-scan, none for symbol-scan — with its real value) straight from the rule data compiled into this binary — never docs/rules/catalog.md prose. Accepts the full <pack>/<rule> id or a bare <rule> id when unambiguous. Two answers are worth knowing about before you need them. An io-scan rule's marker is printed with its run-mode condition attached — native-parse runs only: an envelope carries no source text for the finding's anchor line, so in analyze-envelope mode no marker there suppresses anything and you disable the id or exclude the path instead. (A symbol-scan rule answers none for the same class of reason: its findings have no line to anchor a comment against.) And an issue label — the schema/dead-model-shaped string a finding's ruleId actually spells, accepted bare too — is not a rule id this lookup can render, so it comes back as a guided failure (stderr, exit 1) that names the family gate which DOES exist and which disabledRules takes, rather than the "unknown rule id" a reader of real output used to get for zzop's own output.
zzop-mcp mcpServe MCP over stdio (newline-delimited JSON-RPC 2.0) — what a Claude Code/Desktop config points at.
zzop version / --versionPrint the binary's version (the same value MCP's initialize reports as serverInfo.version).
zzop help / --help / -hPrint the usage line plus one elaboration per subcommand, exit 0 (the zzop-mcp server binary has its own help).

Exit codes are uniform across every subcommand: 0 = ran successfully; 1 = a runtime failure (unreadable path, invalid envelope/config) — for validate-envelope/validate-rule-pack specifically, 1 instead means "ran fine, found the input invalid"; 2 = an argument-shape mistake (missing/extra/flag-shaped argument). There is no severity-gated CI exit code today — failOn is a recognized-but-inert config key (see above); gate a build by parsing the JSON output's findings/crossLayerFindings severities yourself.

Adapt to your stack

Making zzop fit your environment

No two repositories are the same shape, and zzop is meant to be tuned to yours rather than run one-size-fits-all. Every way in is data, not an engine fork:

  • Custom rule packs. Rules are JSON. Put a pack of your own conventions in a directory and point packs.extraDirs at it — a custom pack whose id matches a bundled one wins. The rule catalog shows the shape; zzop validate-rule-pack <pack.json> checks one before you ship it. Full DSL reference: docs/rules/authoring-guide.md.
  • Parser injection for what the engine can't read natively. A language or framework zzop doesn't parse — or a hand-rolled HTTP client it can't see — need not be a blind spot. An external adapter (any language) emits a Normalized-AST envelope, in one of two shapes named after the engine entry point that consumes it: analyzeEnvelope (Mode A — a full envelope that replaces native parsing for a run, via zzop analyze-envelope) or adapterOverlays (Mode B — just the IO/fragment facts for a few files, merged on top of native analysis). Worked adapters ship in the repo (OpenAPI-SDK, Svelte, wrapper, react-query). See NORMALIZED_AST.md and the adapterOverlays field.
  • Topology facts only you know. A gateway mount prefix, which hosts a tree owns, a route zzop couldn't resolve from source — declare them in config (mounts / mountedAt / hosts / routes) so the cross-layer join sees your real deployment shape, not just what's literal in the source.

This is where zzop pairs naturally with an AI agent over MCP: the agent runs an analysis, reads the coverage census and warnings to see exactly what came back dark (a channel with zero extraction, a language with no native parser), and you tune the config or add an adapter together until the map is complete. The tool tells you what it cannot see instead of guessing — so the loop converges on your environment.

Findings

Suppressing & disabling findings

DSL pack rules (the typescript/no-explicit-any, sql/nplus1-style ids) each carry an inline suppress marker — a short comment placed in the flagged code, e.g. // no-explicit-any-ok — that silences just that occurrence. The marker is derived from the rule id, so you never look it up: strip the pack prefix from the finding's id and append -ok (sql/nplus1 → // nplus1-ok). Native analyses are disable-only via config, with two comment-driven exceptions: non-idempotent-write/unsafe-read-endpoint honor a hand-written // idempotent-ok: <reason> on the handler's body-start line or up to 3 lines above it (trailing colon required), and dead-candidates/dead-exports skip files carrying a generated-file banner (@generated and friends) in their first 8 lines.

Disable a native analysis
{
  "rules": {
    "dead-candidates": "off",
    "cross-layer/unconsumed-endpoint": "off"
  }
}

Embedders pass the same ids through disabledRules instead of the rules: { "<id>": "off" } config shape.

Programmatic / embedding

Embedding the engine

Building a tool on top of zzop rather than running it as a CLI? Shell out to this same binary's JSON subcommands — the same engine the CLI drives, JSON in / JSON out, one stable contract, no Node and no separate SDK to install. (The zzop-facade / zzop-summary crates it is built from are workspace-internal and not published to crates.io, so an in-process Rust dependency means vendoring the workspace, not cargo add.) See crates/host/README.md for the JSON subcommand reference.
