ZERO ZONE OF PAIN

zzop

Your AI coding agent can't read your whole codebase. zzop reads it — and answers the same way every time. Point it at one repo, or at your frontend and backend together, and get one JSON map of what is actually there: which calls reach which routes and which reach nothing, what looks risky, what is dead, and what this run could not see. zzop writes no code. It makes the understanding your agent works from accurate and repeatable.

Run it yourself (the zzop CLI)
# download the zzop CLI from GitHub Releases (no Node.js, nothing to compile) —
# or: npm i -g @zzop/cli
zzop analyze .             # analyze this tree, print JSON findings
zzop cross ./web ./api     # join two repos: which calls reach which routes

# Want your AI agent to do the asking instead? That is the other binary,
# zzop-mcp — install the Claude Code plugin and skip the terminal entirely.

SEE IT

Break a route, and watch nothing else notice

Two independently-authored apps — a React frontend and an Express backend — vendored side by side, sharing no code and no types. Rename one backend route. The frontend build stays clean (the route is a string literal, so there is no type to check it against) and its own mocked tests stay green. The contract is broken, and a linter, a type-checker or a test suite scoped to one repository is structurally unable to see it: the evidence is split across two repos and never crosses a compiler boundary.

What zzop reports
- router.put('/user',     auth.required, …)   # the backend tidy-up
+ router.put('/users/me', auth.required, …)   # the frontend is NOT touched

=== unprovided consumes ===
  "PUT /api/user"      @ fe-vite     src/pages/Settings.jsx:19       ← the call now hits nothing

=== unconsumed provides ===
  "PUT /api/users/me"  @ be-express  src/app/routes/auth/auth.controller.ts:61   ← the route nobody calls

Both ends of the break, located to the file and line, across two repos that share nothing on disk. The full walkthrough — including why the frontend's own tooling stays green, and the other drift shapes the same join catches (a changed verb, a removed endpoint, a body field that stopped being returned, a DB table two services disagree on) — is docs/demo/break-a-route.md — a narrated walkthrough that writes out every command and the output it produced, so it reads end to end without you running anything. The script behind it (docs/demo/break-a-route.sh) is a maintainer tool: it builds a cargo example, so it needs a source checkout rather than a released binary, and it analyzes two repositories you supply under a gitignored corpus/oss/ directory that this repo does not ship.

WHY ZZOP

Why zzop

An agent working in a large repository cannot read every file — the context window is its scarcest resource, and what it does not read it infers. zzop condenses the whole codebase into one compact, machine-readable report: what is risky, what is dead, what drifted between frontend and backend, and where to refactor first. Agents and humans alike start from the map, not the territory.

That makes zzop a context provider, not a generator. It writes nothing and suggests no code. What it changes is how accurately the model understands the project it is about to edit — and because the same input produces byte-identical output, that understanding is repeatable rather than re-guessed each session.

That is also where it parts ways with traditional static analyzers. A classic linter or SAST tool hands you a flat list of findings and stops; zzop is built to give direction — every finding names the exact config to silence it (DSL rule findings additionally carry a concrete fix and a one-line suppress marker), structural results are ranked by refactor ROI, and cross-repo joins turn "two codebases quietly disagree" into a first-class, actionable finding.

WHAT IT DOES

One engine, three lenses

Cross-layer

Frontend calls joined to backend routes: unconsumed endpoints, method mismatches, version skew, path drift — even across repositories.

Security (SAST)

SQL injection, weak hashing, SSRF, hardcoded secrets — DSL rules plus native analyses catch vulnerable patterns across languages.

Structure

Circular dependencies, dead code, risk scores, extraction seams — structural debt, quantified per file and per repository.

zzop itself draws nothing: zzop graph serializes a run as text — a mermaid flowchart, or two NDJSON tables — and leaves the picture to a viewer. This repository's own import graph is that output, uncapped, read by a viewer this site carries.

WHAT MAKES IT DIFFERENT

What makes it different

Cross-layer, cross-repo

zzop cross accepts multiple roots and joins them: one repo's frontend fetches against another repo's backend routes. Drift between layers becomes a finding, not a production incident.

Customizable in any environment

Rules are data, not engine code. Write your own packs in a JSON DSL, extend or override the bundled ones with packsDir, and feed languages the engine does not parse natively through the Normalized AST adapter protocol.

Deterministic, honest output

Same input, byte-identical output — no timestamps, no unstable ordering. A capability a run cannot provide is absent and self-reported in warnings, never stubbed. An empty array always means analyzed, found nothing.

One command to start

zzop init writes the config a run needs, every key annotated and already set to zzop's own value. A config is required rather than optional: the names zzop would otherwise guess about your project live in it, and a key you do not declare is a judgment zzop does not make. Every finding names the exact config to silence it deliberately — DSL rule findings additionally carry the concrete fix.

TWO BINARIES

Which one do you want?

zzop ships as two Node-free binaries over one shared engine. Decide which you need before you install anything — a tool call and a CLI run against the same path dispatch through the same handlers and give the identical answer.

zzop-mcp — for your AI agent

An MCP server over stdio. Install the Claude Code plugin or the Claude Desktop .mcpb bundle and the agent calls the tools for you — you run no commands. The tools are analyze_repo, cross_repo, check_file, check_endpoint, analyze_envelope, validate_envelope and validate_rule_pack, alongside the zzop://contract/* resources carrying the authoring contracts. It has no analysis subcommands of its own: bare or mcp serves stdio, version/help are the rest.

zzop — for a terminal or CI

A plain CLI. zzop analyze ., zzop cross ./web ./api, zzop endpoint users … — JSON to stdout, ESLint-style, driven by a zzop.config.jsonc. These lanes are CLI-only, with no MCP tool twin: manifest/diff (commit a structural contract snapshot, diff a later run against it), facts (the uncapped post-assembly substrate for your own rule program), graph (the join as mermaid text), explain and init (write the annotated starter zzop.config.jsonc). There is no mcp subcommand here.

Installing either is covered on one page: Usage → Install.
